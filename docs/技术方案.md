## 1. 目标与范围

### 1.1 产品定义

做一个手机端 App，替代 Google 的 Android Auto 手机端（`com.google.android.projection.gearhead`，内部叫 CarService），自己与车机建立 AA 会话，把「CarLife 式」的车机界面投上去：

- 车机屏幕上出现：导航卡片、音乐、电话、语音、消息、应用列表、设置；
- 手机说、车机显示：视频编码走 H.264，触控/旋钮回传，音频走 AA 音频通道；
- 连接方式：优先 USB 有线（AOA），其次无线（蓝牙引导 + Wi-Fi + TCP），再有一个仅开发用的 ADB/TCP 通道。

**一句话：本质是做一个 AARE 类的「AA 手机端替代实现」，叠加国内用户需要的 CarLife 式功能与中文生态。**

### 1.2 本期范围

| 阶段 | 范围 | 目标 |
|---|---|---|
| P0 可行性验证（4 周） | 协议栈骨架 + 开发通道 + PC 模拟车机 | 手机 App 连上模拟车机，出现首帧画面，触控可用 |
| P1 MVP（2–3 个月） | USB 有线全链路 + 自绘车机 UI + 音频 + 重连 | 在一台真实 AA 车机上跑通导航/音乐/电话 |
| P2 产品化（3–6 个月） | 无线、兼容性矩阵、性能、CarLife 式功能补齐、合规评估 | 可对外试用/定向交付的版本 |

### 1.3 非目标（本方案不做）

- 不做车机端接收端（那是 AARE/openauto/Headunit Revived 那一侧）；
- 不做 CarPlay（MFi 芯片授权，另一条赛道）;
- 不伪造/不内置 Google 签发的证书（是否由用户自行导入，属于产品策略与法务决策，见可行性报告）；
- 不承诺覆盖 Google 私有的、只对 Google 签名的宿主开放的 App（Google 地图、Waze、Spotify 等，见 §7.3）。

### 1.4 术语

| 术语 | 含义 |
|---|---|
| AA | Android Auto，Google 的车机投屏产品 |
| AAP | Android Auto Protocol，AA 的线协议（帧、TLS、protobuf 消息） |
| AOA / AOAP | Android Open Accessory Protocol v2，USB 配件模式握手协议 |
| HU | Head Unit，车机 |
| DHU | Desktop Head Unit，Google 官方的车机模拟器（给 AA 应用开发者用） |
| Car App Library | `androidx.car.app`，Google 官方的「手机 App 在车机上跑」的框架 |
| CarLife | 百度 CarLife，国内主流的手机-车机互联方案 |
| 通道（channel） | AAP 内的逻辑通道：video / media audio / speech audio / input / sensor / control… |

## 2. 总体架构

### 2.1 分层架构

```
┌────────────────────────────── 手机 App ──────────────────────────────┐
│ 应用层（自绘车机 UI）                                                  │
│   导航卡片 │ 音乐 │ 电话 │ 语音助手 │ 消息 │ 应用列表 │ 设置           │
├───────────────────────────────────────────────────────────────────────┤
│ 内容接入层                                                             │
│   自有页面 │ MediaBrowserService 媒体 │ 通知监听 │ 语音 Assistant │ 投屏 │
├───────────────────────────────────────────────────────────────────────┤
│ AAP 会话层                                                             │
│   版本协商 │ 服务发现 │ 通道打开/关闭 │ 焦点管理 │ ping/keepalive │ 关闭 │
├───────────────────────────────────────────────────────────────────────┤
│ 通道服务层                                                             │
│   视频(H.264) │ 媒体音频(PCM) │ 系统/语音音频 │ 麦克风 │ 输入 │ 传感器 │
├───────────────────────────────────────────────────────────────────────┤
│ 安全层：TLS 1.2 双向认证（手机 = TLS server）                          │
├───────────────────────────────────────────────────────────────────────┤
│ 传输层                                                                 │
│   USB AOA 配件模式（主）│ 无线：BT 引导 + Wi-Fi + TCP（次）│ ADB/TCP 5277（开发）│
└───────────────────────────────────────────────────────────────────────┘
                                ▲
                                │ AA 通道（USB / Wi-Fi）
                                ▼
┌────────────────────────────── 车机端 ────────────────────────────────┐
│ 车机 AA 接收端（Google 认证实现 / 后装 AA 接收模块 / 开源实现）        │
│ 视频解码显示 │ 触控采样 │ 音频播放 │ 传感器上报 │ 车机 UI 外壳          │
└───────────────────────────────────────────────────────────────────────┘
```

### 2.2 三条连接通道

| 通道 | 用途 | 必需条件 | 优先级 |
|---|---|---|---|
| USB AOA | 量产主通道，最稳、带宽足够 | 车机 USB 口支持 AA；手机打开 USB 调试不是必需（配件模式走系统广播） | P0 |
| 无线（BT + Wi-Fi + TCP） | 体验型通道，车机不带线 | 车机支持无线 AA；手机与车机先蓝牙配对 | P2 |
| ADB / TCP 5277（head unit server） | **只有开发调试用**，无车机也能联调 | USB 调试 + `adb forward`；对端是 PC 上的模拟车机 | P0（联调台架） |

> 说明：AA 的「手机端」在 TLS 握手中是 **server**（车机是 client），所以无论是 TCP 还是 USB 管道，手机端都要能「等对端发起 TLS」。这一点决定了开发通道可以直接复用协议栈。

### 2.3 内容呈现的三种策略

| 策略 | 做法 | 优点 | 缺点/门槛 | 建议 |
|---|---|---|---|---|
| **S1 自绘车机 UI**（推荐起步） | 在私有 VirtualDisplay 上跑自己的 Compose 界面，输入事件直接进自家 UI 框架 | 不需要 root/Shizuku/无障碍；体验可控；最像 CarLife | 内容生态要自己接 | P0/P1 采用 |
| **S2 Car App Library 宿主** | 实现 `androidx.car.app` 的宿主，渲染第三方模板应用（CoMaps/OsmAnd 等海外开源地图） | 白拿一批第三方应用 | 工程量大；国内 App 基本不接 Car App Library；部分应用校验宿主签名 | P2 评估 |
| **S3 系统投屏镜像** | `MediaProjection` 抓屏 + 触控注入 | 「整机投屏」卖点 | 触控注入需要无障碍/Shizuku/root；锁屏、隐私、功耗、安全都有坑 | 可选功能，默认关闭 |

## 3. 连接层：USB AOA 有线

### 3.1 握手流程

AA 有线连接本质是标准的 Android 开放配件协议（AOA v2）：

1. 车机（USB Host）枚举到手机（普通 Android 设备）；
2. 车机通过 USB 控制传输发送 AOA 请求：
   - `51` = ACCESSORY_GET_PROTOCOL（探测是否支持 AOA，返回 2）；
   - `52` = ACCESSORY_SEND_STRING（下发 accessory 描述符：manufacturer / model / description / version / URI / serial）；
   - `53` = ACCESSORY_START（让手机切换到配件模式）；
3. 手机重新枚举为 **Google Accessory（VID `0x18D1`，PID `0x2D00`/`0x2D01`）**；
4. Android 系统发出 `android.hardware.usb.action.USB_ACCESSORY_ATTACHED` 广播，匹配 `usb-accessory` intent-filter 的 App 收到 `UsbAccessory`；
5. App 通过 `UsbManager.openAccessory()` 拿到文件描述符，用 bulk 端点双向读写；
6. 在管道上开始 AAP：版本请求/响应 → TLS → 认证 → 服务发现 → 打开通道 → 推流。

### 3.2 手机端 App 的注册与「抢应用」

- 在 `AndroidManifest.xml` 里声明配件 intent-filter（`USB_ACCESSORY_ATTACHED` + `<usb-accessory manufacturer=… model=… version=… />`），具体匹配串需要按目标车机实际下发的描述符抓取确认；
- 如果手机同时装了 Google 的 Android Auto，**两个 App 都会响应同一个配件**，Android 会弹「用哪个应用打开」，用户选「始终」后固定（AARE 的 README 已明确描述了这个行为）。这对我们有利：**第三方 App 在系统层面是有机会接管 AA 配件连接的**；
- 注意：不同车机的 accessory 描述符不同，需要做白名单/通配 + 实测矩阵。

### 3.3 权限与各 Android 版本差异（易踩坑）

| 版本 | 坑 | 对策 |
|---|---|---|
| Android 12+ | 普通 App 读不到真实蓝牙 MAC（返回 `02:00:00:00:00:00`） | 让用户手动填/配置文件注入（AARE 的做法）；或在设置页引导 |
| Android 13+ | 通知监听、附近设备、`POST_NOTIFICATIONS` 等权限收紧 | 首次启动引导页逐项申请 |
| Android 14/15+ | 前台服务类型（`mediaProjection`、`connectedDevice` 等）必须声明 | Manifest 声明类型 + 运行时校验 |
| Android 17 | 无线/局域网连接需要「本地网络」权限，否则静默丢包 | 连接前申请并检测 |

### 3.4 无线通道（P2）

1. 手机与车机先蓝牙配对；
2. 车机通过蓝牙通道下发 Wi-Fi 连接信息（车机开 AP，或手机连车机热点）；
3. 手机加入网络后，车机以 TCP 连接手机的 5277 端口（手机端监听）；
4. 之后的 TLS/AAP 与有线完全一致。

无线相比有线多出的坑：2.4G/5G 干扰、车机 AP 切换、回连、VPN 冲突（VPN 网段与车机网段重叠）、Android 17 本地网络权限。

### 3.5 开发通道（无车机联调，P0 的关键）

AA 官方有一个开发者功能：手机端在「开发者设置」里开启 **head unit server**，通过 ADB 转发 TCP 5277 给 PC 上的 DHU 使用。AARE 也实现了同样的「head unit server」：

```bash
adb forward tcp:5277 localabstract:<your-app-socket>
# PC 上的模拟车机连 localhost:5277
```

我们自己实现的手机端 App 也应实现这个模式（仅 debug build 或设置页里显式开启）。这样：

- **不用买车机、不用 USB Host 硬件**就能联调协议、TLS、视频、触控；
- 对端可以直接用 AARE 的桌面车机（`headunit.sh`，Java 17–21 + adb + ffmpeg，可在 Windows 的 Git Bash/WSL 下跑）或 openauto 的 headless 模式；
- 注意：这是「调试后门」，务必默认关闭、只在本地回环或经 adb 转发时可用，避免被同网段设备直接连接（AARE 默认一次会话后自动关闭网络模式，是有安全原因的）。

## 4. 安全层：TLS 与证书

### 4.1 握手与角色

- TLS 1.2，**手机是 server，车机是 client**；**双向认证**（mutual TLS），双方都要出示证书；
- 握手发生在 AAP 的加密消息里（control channel / message type 3 `ENCAPSULATED_SSL`）；
- 握手完成后车机发 `AUTH_COMPLETE`（message type 4），状态 0 = 接受，负值 = 拒绝。

### 4.2 证书链

| 证书 | Subject | Issuer | 有效期 |
|---|---|---|---|
| 根 | `O=Google Automotive Link` | 自签 | 2014-06-06 → 2044-06-05 |
| 手机端叶证书 | `O=CarService` | Google Automotive Link | 2014-07-04 → **2026-12-31** |

关键结论（均有公开实测支撑，见 [AARE 证书文档](https://github.com/prototux/AARE/blob/main/docs/certificates.md)）：

1. **Google 的 AA 只接受「由 Google 签发车机证书」的车机**（所以自制车机连不上官方 AA）；
2. **车机是否校验手机端证书，因车机而异**：
   - Google 官方 DHU：校验，非 Google 证书会被拒（`AUTH_COMPLETE` 状态 `-3`）；
   - 基于 Google 接收库的原厂车机：**大概率校验**（社区实测有例外，如 2026 款丰田 Land Cruiser 79 的 Denso Ten 车机就不校验）；
   - 开源车机（openauto / Crankshaft / Headunit Revived / LIVI / aa-proxy-rs）：不校验；
   - 部分后装/OEM 车机：视实现而定，**必须实测**；
3. 状态码：`-3` 认证失败、`-23` 证书尚未生效、`-24` 证书过期；
4. 手机端证书由 Google 放在 AA APK 里（每次安装都是同一张证书 + RSA-2048 私钥，加密存储），Google 大约每 8 个月轮换，现行叶证书 **2026-12-31 到期**。到期后，会校验证书有效期的车机会拒绝连接——**任何依赖该证书的方案都有硬到期日**。

### 4.3 产品策略（合规与风险的分界点）

| 策略 | 描述 | 技术效果 | 风险 |
|---|---|---|---|
| **自带证书（自签）** | App 首次启动生成自签证书；车机不校验就能连 | 兼容不校验的车机（开源车机、部分后装、少数原厂） | 零证书风险；覆盖面窄 |
| **用户自行导入证书** | 设置页支持导入 PEM/PKCS#12；App 不内置、不下载 | 兼容校验证书的大部分车机 | 证书来源属于用户行为；产品仍有「帮助规避」的风险，需法务评估 |
| **内置/自动下载 Google 证书** | AARE 的做法（从第三方仓库一键下载） | 兼容面最大 | **明确违规/侵权风险**；商用不可取 |

**工程实现要求**：证书加载/切换必须做成可插拔、可热更新（不重新发版也能换证书），并在连接日志里明确打出当前证书指纹与失败状态码，方便现场排障。本文不提供提取 Google 私钥的方法。

### 4.4 车机端证书的信任

车机（TLS client）也会给手机出示证书。手机端策略建议：

- 记录每个车机证书的 SHA-256（按 accessory 描述符/无线配对信息做键）；
- 首次连接让用户「信任这台车机」，之后证书变化要提示（防中间人/充电桩伪装）；
- 开源车机的证书是公开私钥（openauto/aasdk/DHU 内置），只能防「没见过的证书」，防不了拿到公开私钥的人——这点要在设计里说清楚，不要当成强安全边界。

## 5. AAP 协议层

### 5.1 帧与消息

- 底层是字节流（USB bulk / TCP），上面是**帧（frame）→ 消息（message）**：一帧承载一条消息，超长消息分片，实现中常见以 **16 KB** 为界处理；
- 通道 0 = control channel，其余为业务通道；
- 所有消息体是 protobuf（`aap` 目录里约 250+ 个定义，来源于社区逆向，公开可得的权威参考是 [opencardev/aasdk](https://github.com/opencardev/aasdk) 的 `proto` 目录）。

### 5.2 会话状态机（手机端视角）

```
IDLE
 └─(对端连上/AOA 管道就绪) → WAIT_VERSION
      ├─ 收到 VERSION_REQUEST → 回 VERSION_RESPONSE（目标 1.7，兼容 1.5/1.6）
      → TLS_HANDSHAKE（手机作为 TLS server）
      ├─ 握手失败/对端拒绝 → 记录状态码，回 IDLE（可换证书重试）
      → AUTHENTICATED（等车机 AUTH_COMPLETE）
      → SERVICE_DISCOVERY（车机请求 → 手机回通道列表）
      → CHANNELS_OPEN（逐个 CHANNEL_OPEN_REQUEST/RESPONSE）
      → RUNNING（视频/音频/输入/传感器）
      ├─ 对端 BYE / 物理断开 → CLEANUP → IDLE（指数退避重连）
      └─ 长时间无 ping → 判定假死 → 主动断开重连
```

### 5.3 业务通道（按实现优先级）

| 通道 | 方向 | 内容 | 优先级 |
|---|---|---|---|
| control | 双向 | 版本、TLS、认证、服务发现、通道开关、ping、焦点、关闭 | P0 |
| video | 手机 → 车机 | H.264 码流（关键帧/帧时间戳/ack 流控） | P0 |
| input | 车机 → 手机 | 触摸（单点/多点）、按键、旋钮 | P0 |
| media audio | 手机 → 车机 | 媒体音频（PCM） | P1 |
| speech audio / system audio | 手机 → 车机 | 语音播报、提示音 | P1 |
| audio input（麦克风） | 车机 → 手机 | 车机麦克风音频 | P1 |
| sensor | 车机 → 手机 | 日夜模式、行驶状态、车速、档位、GPS、罗盘 | P1 |
| bluetooth / phone status | 双向 | 蓝牙配对信息、通话状态 | P2 |
| navigation / media browser / notification | 双向 | 仪表盘导航、媒体浏览、通知 | P2 |
| cluster（仪表） | 手机 → 车机 | 仪表盘视频（部分车机支持） | P3 |

### 5.4 焦点与生命周期

- **音频焦点**：车机可能随时抢占（收音机、倒车雷达、电话），手机收到焦点变化后要暂停/恢复媒体，并处理「暂不恢复」；
- **视频焦点**：车机切倒车影像时会收回屏幕，必须暂停视频编码，否则花屏/黑屏；
- **导航焦点**：导航类内容在车机上有独立焦点，决定导航卡片/仪表盘显示；
- **优雅关闭**：收到对端 `BYE`/`SHUTDOWN` 时按顺序关通道、停编码器、释放 Surface；
- **重连语义**：车机休眠/点火、USB 供电抖动（VBUS 断开）是常态，实现必须有「断线检测 → 指数退避 → 恢复首帧 IDR」的完整逻辑（AARE 的 connection-stability 文档有很细的实测经验）。

**结论**：
- **P0/P1 阶段**（自用、验证、开源项目）：可以直接 fork AARE，最快；
- **闭源商用**：必须 clean-room 重写协议层（基于公开的协议行为观察、不抄代码、不抄 GPL 的 `.proto` 文本），或取得作者授权；这是一笔实打实的成本与法务工作，不能省。

## 6. 媒体管线

### 6.1 视频

| 项 | 建议 |
|---|---|
| 采集方式 | **私有 VirtualDisplay + 自绘 UI**（S1 策略）；`MediaProjection` 只用于可选的 S3 投屏 |
| 编码 | `MediaCodec` 硬件 H.264（Baseline/High），`COLOR_FormatSurface` 直通 |
| 分辨率 | 由车机 SERVICE_DISCOVERY / VideoConfig 协商；起步 1280×720，兼容 800×480、1920×720 超宽 |
| 帧率 | 30 fps；**事件驱动**（UI 有变化才编码，空闲每 2 s 补一帧）可大幅降功耗和带宽 |
| 码率 | 4–20 Mbps 自适应：车机 ack 落后/无线弱时降码率，恢复后升 |
| 关键帧 | 首帧必须等 IDR；每个关键帧前附 SPS/PPS（Annex-B）；断线重连后强制 IDR |
| 时间戳 | 微秒级、以 0 为基准；与 ack 流控配合，防解码器花屏 |
| 焦点 | 车机收回视频焦点（倒车影像、系统弹窗）→ 立即暂停编码、停 Surface；恢复后再推 IDR |

参考实现：mretallack/AndroidAuto 的「800×480@30fps Baseline + MediaProjection + 事件驱动 + max_unacked 流控」是最小可用版本；AARE 的实现覆盖 4K/超宽屏/横竖屏/仪表盘，可作为「豪华版」参考。

### 6.2 音频

AA 用的是「手机编码 → 车机播放」的独立音频通道（媒体/系统/语音/麦克风），默认 PCM。难点不在编码，而在**在手机侧合法地把声音抓出来**：

| 方案 | 能力 | 前提 | 建议 |
|---|---|---|---|
| 自绘 UI 内直接产生音频 | 自家播放器/导航播报直接拿 PCM | 无 | **P0 采用** |
| `AudioPlaybackCapture` | 捕获其他 App 的媒体音频 | Android 10+；App 可声明禁止被捕获；导航语音不在内 | P1 可用（播客/音乐） |
| 系统音频路由（`MODIFY_AUDIO_ROUTING`） | 与官方 AA 一致，媒体/导航分通道 | 特权 App / root / Shizuku | P2 选配 |
| 蓝牙 HFP 兜底 | 车机保持通话/媒体蓝牙 | 无 | 兜底方案 |

配套：音频焦点请求/丢失/恢复、静音保活策略（无声音时关闭通道，有声音再开，避免车机一直占用）、麦克风通道（车机麦克风 → 语音助手）。

### 6.3 输入与传感器

- **触控**：车机坐标 → 手机 UI 坐标的映射要做分辨率归一化 + 安全区适配；单点/多点；旋钮/方向键/媒体键/语音键/返回键映射；
- **驾驶限制**：行驶中锁输入（长列表、键盘、设置项默认禁用），这是安全要求也是应用商店合规要求；
- **传感器**：车机的 GPS 通常比手机好，应优先用车机 GPS 喂导航；日夜模式、车速、档位、手刹、行驶状态用于 UI 与锁定策略；
- **仪表盘（cluster）**：部分车机支持第二块屏，P3 再做，投入产出比低。

## 7. 应用层：CarLife 式体验怎么做

### 7.1 车机界面结构

- **首页**：任务栏/侧栏（语音、主页、返回、最近应用）+ 卡片区（导航地图卡、音乐卡、下一条日程/通知、天气、时间）；
- **导航**：自绘地图（接第三方地图 SDK 或瓦片 + 自建路线）或「手机导航 App 的通知文本 + 语音播报」的轻量方案；
- **音乐**：`MediaBrowserService`/`MediaSession` 浏览与播放控制，本地播放器 + 第三方 App 的媒体会话；
- **电话**：`TelecomManager` 状态 + 通讯录/最近通话；通话音频走车机蓝牙 HFP（手机端不改通话链路）；
- **语音**：车机麦克风 → 手机语音助手（系统 Assistant 或自研），支持「导航/播放/读消息/回复」等车控指令；
- **消息**：`NotificationListenerService` 抓取会话 → 朗读、标记已读、停车时语音/键盘回复；
- **设置**：主题、日夜、分辨率/密度、连接管理、证书与信任管理、日志导出。

### 7.2 国内 App 内容接入的真实边界（重要）

这是本项目与 CarLife 最大的差距，必须在立项时认清：

| App | AA / Car App Library 支持 | 我们能拿到的 | 结论 |
|---|---|---|---|
| 高德 / 百度 / 腾讯地图 | ❌ | 导航通知文本、语音播报、媒体会话；投屏（可选） | 只能做「导航卡片 + 播报」，无法内嵌其车机界面 |
| QQ 音乐 / 网易云 / 酷狗 | ❌ | `MediaSession`/`MediaBrowserService` 播放控制与元数据 | 可控制播放，但拿不到它们自己的车机 UI |
| 喜马拉雅等音频 | ❌ | 同上 | 同上 |
| 微信 / 钉钉 | ❌（国内 IM 不接 AA 通知规范） | 通知监听（可读文本，但隐私与合规风险大） | 谨慎，需用户显式授权 |
| 海外开源地图（CoMaps/OsmAnd/Organic Maps） | ✅ Car App Library | 完整模板/地图 Surface | 可作 S2 生态亮点，但国内用户少 |

CarLife 能「把第三方 App 搬进车机」，是因为百度与这些 App 有商务合作（服务端白名单、内置入口、HMI 规范）。**第三方 AA 手机端拿不到这种合作**，只能使用 Android 公开接口。因此产品上要设计成「聚合系统能力」而不是「复刻 CarLife 的应用商店」。

### 7.3 被 Google 锁住的 App（不要承诺）

Google 地图、Waze、Spotify 等一批 App 只对 Google 签名的宿主开放（校验宿主签名/使用私有接口/签名级权限）。非 Google 实现（AARE 也一样）在未 root 设备上无法显示它们，只能拿通知和语音。**这是产品边界，不要在需求里写「支持全部 AA 应用」。**

### 7.4 与 CarLife 互通的可能性

- 百度 CarLife 手机端是**封闭 App**，没有面向个人的第三方接入；
- CarLife 车机端协议（6 条 TCP 通道、AOA/USB、H.264/PCM、可选加密）虽然可逆向，且已有开源实现与「本机码流劫持」实验（如 CarPToCarL），但**无官方授权**；
- 中国已有判例把「让车机误认为适配器是 CarLife 认证手机端」认定为不正当竞争（见可行性报告 §5）。**建议不要在商用产品里做 CarLife 协议互通或冒充。**

## 8. 工程实现

### 8.1 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | Kotlin（100%） | AARE 已证明纯 Kotlin 可完成手机端全套 |
| UI | Jetpack Compose（跑在私有 VirtualDisplay 上） | 车机界面分层、主题、深浅色 |
| 并发 | Coroutines + Flow + Channel | 通道读写、编解码、状态机 |
| TLS | Conscrypt（Android 自带）或 BouncyCastle | 需要自定义 KeyManager/TrustManager |
| 序列化 | protobuf-javalite | `.proto` 需 clean-room 或按 GPL 开源 |
| 媒体 | MediaCodec / MediaProjection / AudioRecord / AudioTrack | 硬件编解码优先 |
| 构建 | AGP 8.x + Gradle 8.x，JDK 17/21，compileSdk 35+，minSdk 26 | 低版本兼容按目标机型调整 |
| 测试 | JUnit + 自研「模拟车机」（JVM） | 协议层可在 PC 上单测 |

### 8.2 建议目录结构

```
app/                     手机端 UI、设置、引导、日志
core/transport/          USB AOA、TCP server、无线引导（BT+WiFi）
core/protocol/           AAP 分帧、TLS、会话状态机、通道管理
core/media/              H.264 编码器、音频采集、麦克风、码率控制
core/ui-car/             车机界面组件（Compose）、主题、布局
feature/nav/             导航卡片/地图
feature/music/           媒体浏览与播放
feature/phone/           通话与通讯录
feature/voice/           语音与会话
feature/msg/             通知与消息
feature/mirror/          MediaProjection 投屏（可选）
sim-headunit/            PC 端模拟车机（JVM，用于无车机联调）
```

### 8.3 权限清单（易被忽略的）

`FOREGROUND_SERVICE` + 对应 type（`connectedDevice`/`mediaPlayback`/`microphone`）、`POST_NOTIFICATIONS`、`RECORD_AUDIO`、`BLUETOOTH_CONNECT`/`BLUETOOTH_SCAN`、`READ_PHONE_STATE`/`READ_CALL_LOG`/`READ_CONTACTS`（电话功能）、`BIND_NOTIFICATION_LISTENER_SERVICE`（消息）、`SYSTEM_ALERT_WINDOW`（可选）、无障碍/Shizuku（仅投屏触控）、`MANAGE_EXTERNAL_STORAGE`（不要用）。注意 `QUERY_ALL_PACKAGES` 和通知监听/无障碍都是应用商店严审项；侧载可绕开但商用风险仍在。

### 8.4 构建与验证环境

- 需要：JDK 17–21、Android SDK（platform 35、build-tools）、一台 Android 手机；
- 当前开发机没有 JDK / Android SDK，且命令行无外网（无法下载），**本报告阶段无法编译 APK**；源码与构建脚本可以交付，实际编译需在装有 Android Studio 的机器上做；
- 推荐用 Android Studio 打开工程 + USB 真机调试，配合 §9 的模拟车机。

### 8.5 稳定性（车机场景的第一优先级）

- 连接状态机 + 看门狗（无 ping 30 s 断开重连）；
- 指数退避重连、USB VBUS 断电检测、点火/休眠唤醒恢复；
- 首帧前不渲染黑屏/花屏（等 IDR）；音频不爆音（预填充/淡入）；
- 连接日志可导出（含证书指纹、协议版本、车机描述符、每通道时间线），这是远程排障的生命线；
- 低功耗：事件驱动视频 + 息屏策略 + 避免常驻前台。

## 9. 测试与验证方案

### 9.1 无车机联调（P0 必须搭好）

| 台架 | 组成 | 用途 |
|---|---|---|
| **A. AARE 桌面车机** | PC（Windows/macOS/Linux）+ JDK 17–21 + adb + ffmpeg，跑 AARE 的 `headunit.sh` / `aare-headunit` | 最接近真实车机；手机 App 实现 head unit server 后 `adb forward tcp:5277 localabstract:<socket>` 即可连 |
| **B. openauto headless** | Docker + openauto + `adb reverse tcp:5000 tcp:5100` | mretallack/AndroidAuto 用的现成联调方式，适合验证协议细节 |
| **C. Open Headunit（原 Headunit Revived）** | 一台 Android 平板/盒子装上 | 真 Android 车机环境的廉价替代 |
| **D. Google DHU** | Android Studio SDK Manager → `extras;google;auto` | **只用于 Car App Library 应用**（官方 AA 应用）测试，不能测我们的自研手机端（证书不通过） |

协议层还应做 JVM 单测：分帧、TLS 握手、版本协商、服务发现、通道状态机、以及「模拟车机 ↔ 手机端」环回的完整会话测试（AARE 的 `:aap:test` 就是这种思路）。

### 9.2 真车机兼容性矩阵（P1 必做）

| 字段 | 说明 |
|---|---|
| 品牌/车型/年款 | 或后装车机型号 + 固件版本 |
| 车机 AA 实现来源 | Google 接收库 / 自研 / 开源（决定是否校验证书） |
| 连接方式 | USB / 无线 |
| 协议版本 | VERSION 协商结果 |
| 证书校验 | 接受自签？拒绝？（记录 `AUTH_COMPLETE` 状态码） |
| 首帧 / 触控 / 音频 / 仪表盘 | 逐项打勾 |
| 30–120 分钟稳定性 | 断连次数、花屏、音频断续 |
| 结论 | 可用 / 部分可用 / 不可用 + 原因 |

参考数据：AARE 已公开 46 台车的实测结果——**22 台完全可用、14 台有问题、少数不可用**，并维护了每台车的适配参数。这说明「能不能连」高度依赖车机型号，必须靠矩阵实测，不能靠猜。

### 9.3 性能指标（验收线）

| 指标 | 目标 |
|---|---|
| 连接首帧 | ≤ 2–3 s（USB） |
| 触控端到端延迟 | ≤ 100 ms |
| 视频 | 30 fps，720p 起步，弱链路自适应降码率 |
| 断线重连 | ≤ 5 s，自动恢复 |
| 稳定性 | 连续 2 h 无崩溃、无花屏、音频无爆音 |
| 功耗 | 亮屏投屏时手机温升可控（此项常被忽略，实测再定预算） |

### 9.4 参考对象的已知坑（直接抄作业）

- Android 12+ 蓝牙 MAC 被屏蔽；Android 17 本地网络权限；
- 车机 VBUS 会在会话中断电（部分车型），必须把「USB 供电断开」当成正常事件处理；
- 一些车机触摸坐标有偏差（AARE 有 per-car 覆盖配置）；
- 部分车机对音频 ack 不响应、对视频 ack 延迟，要做超时兜底。

## 附录 A：协议速查

### A.1 USB AOA 控制请求

| 请求 | 编号 | 作用 |
|---|---|---|
| ACCESSORY_GET_PROTOCOL | 51 | 探测 AOA 版本（返回 2 表示支持 v2） |
| ACCESSORY_SEND_STRING | 52 | 下发 6 个描述符字符串（manufacturer/model/description/version/URI/serial） |
| ACCESSORY_START | 53 | 切换手机到配件模式，重新枚举为 `18D1:2D00`（或 `2D01` = 配件 + ADB） |

> 官方 HUIG 下发的典型描述符：`Android` / `Android Auto` / `Android Auto` / `1.0`；Gearhead 的 accessory filter 为 `manufacturer="Android"`，model ∈ {`Android Auto`, `Android Open Automotive Protocol`, `Android`}。自研手机端 App 的 `<usb-accessory>` 声明需要按这些值（可先通配，再按实测收敛）。

## 附录 C：待确认问题（影响方案取舍）

1. **「CarLife 手机」的确切含义**：是「装了百度 CarLife 的手机」，还是「泛指普通安卓手机、要 CarLife 式体验」？两者结论完全不同（前者不可行，后者可行但受限）。
2. **目标市场**：海外（GMS 手机 + AA 车机）还是国内（无 GMS、AA 车机保有量小）？决定内容生态与商业模式。
3. **开源 or 闭源商用**：决定能否直接 fork AARE（GPL）还是必须 clean-room。
4. **是否接受「用户自行导入证书」的产品形态**：这是兼容原厂车机的现实前提，也是法律风险的分界点。
5. **是否同时做车机端**：两端都做 → 可做私有协议，绕开 Google 证书，但就不是「走 AA 通道」了（见可行性报告路线 D）。
6. **周期与预算**：4 周 PoC / 3 个月 MVP / 6 个月产品化，是否匹配。
